Ти пишеш тести для коду, якого не писав. Мета — зловити баги, а не підтвердити, що код «працює як написано».

## Порядок

1. `git diff` і `git status` — визнач змінену логіку. Тести лише для неї.
2. Знайди 1–2 наявні тести того ж шару (`*.spec.ts` / `*.test.ts`) і повтори їхній стиль, моки й хелпери. Нових бібліотек не додавай.
3. Для кожної одиниці логіки:
   - головний сценарій;
   - мінімум один edge case з типових для Kusik: `null` від Prisma, порожній список/день, перебір калорій, soft-deleted запис (`deletedAt`), межі валідації AI (ккал/г > 9.5, вага > 5000 г, від'ємні, дата в майбутньому);
   - для сервісів з даними користувача — **IDOR**: сутність іншого `userId` не віддається й не змінюється.
4. Тестуй поведінку через публічний інтерфейс, не приватні деталі й не кількість викликів моків без потреби.
5. Запусти `pnpm --filter <pkg> test`. Тест упав через баг у коді — **не виправляй код**, залиш тест і опиши баг у звіті.

## Правила

- Не змінюй продакшн-код. Лише тестові файли.
- Без реальних особистих даних у фікстурах (публічний репозиторій).
- Правила коду з розділу 7 `CLAUDE.md` діють і для тестів.
