# ai-eval

Перевірка якості розбору їжі: той самий запит, промпт і валідація, що й у бекенді (`packages/shared/src/ai`).

```bash
pnpm --filter ai-eval eval --estimate --models a,b   # оцінка вартості: без ключа, без запитів до моделей
pnpm --filter ai-eval eval --stage 0.10.2 --stage-cap 1   # створити бюджет етапу (без прогону)
pnpm --filter ai-eval eval --stage 0.10.2 --only id1,id2 --max-cost 0.5   # кілька текстів
pnpm --filter ai-eval eval --stage 0.10.2 --smoke       # фіксований дешевий набір (src/cases/smoke.ts)
pnpm --filter ai-eval eval --stage 0.10.2 --smoke --only id1   # об'єднання (без дублів)
pnpm --filter ai-eval eval --stage 0.10.2 --models a,b,c   # повний прогін: лише за явним проханням автора
pnpm --filter ai-eval eval --stage 0.10.2 --only id --reasoning minimal   # режим роздумів
pnpm --filter ai-eval eval --rescore results/<файл>.jsonl   # перерахунок метрик із збережених відповідей: без мережі, ключа й --stage
```

Модель — з `AI_MODEL` (`apps/api/.env`). Платні запити йдуть **лише** з `OPENROUTER_EVAL_API_KEY` — окремого ключа OpenRouter з місячним лімітом, який автор вписує в `apps/api/.env` (виробничий `OPENROUTER_API_KEY` не використовується; без eval-ключа прогін відмовляє до будь-якого запиту). `--stage` обов'язковий для кожного платного прогону (не для `--estimate` і створення бюджету). `--max-cost` (за замовчуванням $3) зупиняє прогін. Резерв на кейс = p95 реальних витрат цих кейсів із `results/` × 2 (мінімум $0.02; перший кейс прогону — не менше $0.07 на холодний префікс); без історії — оцінка за ціною моделі. Повні результати — у `results/` (у `.gitignore`).

## Результати прогону (`results/`)

- `<старт>.jsonl` — створюється на старті прогону; **кожен завершений кейс дописується окремим рядком одразу** (той самий `CaseResult` + `promptVersion`, `reasoning`; `model` уже в ньому). Перервений прогін (Ctrl+C, збій) не втрачає оплачених кейсів.
- `<старт>.json` — підсумок наприкінці прогону (масив по моделях, як і раніше; той самий штамп часу).
- У кожному результаті є `rawAttempts` — сирі відповіді моделі по спробах: `toolCalls` (ім'я + рядок аргументів як є), `text`, `isTruncated`. Без запиту й промпту, тож файл компактний.
- **Ctrl+C**: нові кейси не стартують, кейси в роботі дописуються, журнал етапу відображає витрату, код виходу 130; другий Ctrl+C виходить одразу (журнал уже актуальний).

### `--rescore <файл.json|.jsonl>`

Перераховує всі метрики й звіт за збереженими сирими викликами: **поточним** кодом розбору/валідації й **поточними** очікуваннями кейсів. Жодних запитів, ключ і `--stage` не потрібні. Кейси, яких уже немає, пропускаються (друкується кількість). Файли, збережені до появи `rawAttempts`, відхиляються з поясненням — перерахувати можна лише нові. Вартість і латентність беруться зі збереженого. Новий файл не пишеться.

## Політика витрат

1. Зміна лише коду (без промпту, контексту моделі, інструментів, моделі) — eval не потрібен.
2. Кілька текстів — `--only`, не більше 30 кейсів і ≤ $0.5.
3. Багато текстів — `--smoke`: публічні id з `src/cases/smoke.ts` плюс, якщо файл є, `data/private/smoke.private.json` (`{ "ids": ["private:…"] }`, у `.gitignore` разом із `data/private/`; приватні id не лежать у git). Немає файлу — лише публічні. Якщо приватних кейсів немає, відмовляє з кількістю відсутніх (id не друкуються).
4. Повний прогін — лише за явним проханням автора, не частіше разу на місяць.
5. Завжди спершу `--estimate` і «так» автора; бюджет етапу за замовчуванням $1 (`--stage-cap 1`).

## Бюджет етапу (`--stage`)

Журнал `data/private/eval-budget-<етап>.json` (у `.gitignore`) веде `capUsd`, `spentUsd` і список прогонів (кількість кейсів і витрата; з `--only` — лише кількість id). Створюється один раз: `--stage 0.10.2 --stage-cap 4` (повторно — відмова). Без журналу прогін з `--stage` не стартує.

- Жорсткий ліміт прогону = `min(--max-cost, capUsd − spentUsd)`; якщо залишок ≤ 0 — відмова.
- М'яка зупинка на 80 % стелі етапу (накопичено: журнал + цей прогін + резерви кейсів у польоті): нові кейси не стартують, поточні дописуються, результати зберігаються, у виводі лише кількість нестартованих кейсів, у журналі `stoppedAt80`, код виходу 2. `--past-80` вимикає м'яку зупинку (жорсткий ліміт лишається) — лише після явного «так» автора.
- Витрата дописується в журнал **після кожного завершеного кейсу** (сума в журналі = сума завершених кейсів навіть після Ctrl+C чи збою); запис атомарний (тимчасовий файл + rename), записи ставляться в чергу.
- Без `--stage` у терміналі друкується накопичена витрата на 25 / 50 / 80 % ліміту прогону (так само з `--stage`).

## Метрики

- **ккал і білок** — % від еталону, окремо для **точних** (етикетки, зважені продукти, USDA) і **діапазонних** (страви «на око»: усередині діапазону — 0 %, поза ним — до найближчої межі). Мінімальна база — 50 ккал / 5 г білка, щоб малі значення не роздували похибку.
- **категорії** — частка очікуваних категорій, знайдених серед записаних позицій (окремо від ккал: категорія впливає лише на іконку).
- **рішення** — `log` / `clarify` / `not_food` / `reply` (+ `log_or_clarify`, коли обидва допустимі; для `reply` — обов'язкові факти, напр. залишок ккал).
- повтори, збої валідації, обрізані відповіді (`OUTPUT_TRUNCATED`), відповіді без інструмента, $ і токени (з cached) на запит, латентність p50/p95.
- **уточнення:** для кейсів з очікуваним `clarify` — причина, якщо питання не дійшло: модель не спитала / спитала, але нижче порогу / позиція покрита збереженим продуктом (`expect.clarifyAbout`, без уточнень у тексті). Окремий рядок «рішення з урахуванням пам'яті» вважає останній випадок правильним `log`.

## Свої кейси (`data/private/`)

Реальні прийоми їжі не комітяться: `data/private/` у `.gitignore`, eval підхоплює файли, якщо вони є.

- `*.cases.json` — масив кейсів у тому ж форматі, що й у `src/cases` (`id`, `text`, `expect`, `reference`);
- `*.foods.json` — збережені продукти (MyFood): `name`, `aliases`, `per100g { kcal, protein, fat, carbs }`, `pieceGrams`, `defaultGrams`, `category`. Модель бачить ті, що згадані в тексті кейсу, як `m1…`, а цифри записів з пам'яті eval перераховує з `per100g`, як бекенд.

```json
[
	{
		"id": "my-breakfast",
		"text": "вівсянка 60 г на воді і банан",
		"expect": {
			"decision": "log",
			"kcal": { "min": 300, "max": 360 },
			"categories": ["porridge", "banana"]
		},
		"reference": "зважено вдома, етикетка вівсянки 366 ккал/100 г"
	}
]
```

`--set private` — прогін лише приватних кейсів, `--set repo` — лише синтетичних. У терміналі — агреговані метрики й id кейсів, тексти не друкуються.

### Кейси з фото

Фото лежать поруч, у `data/private/` (наприклад `data/private/photos/`), і теж не комітяться. Кейс отримує `image` — шлях відносно `data/private/` (`.jpg`, `.png` або `.webp`); `text` тоді необов'язковий. Фото йде в модель як є — поклади вже таке, яке надіслав би застосунок (довша сторона до 1568 px, до 1 МБ JPEG), інакше eval лише попередить. У `results/` потрапляють id і цифри, самого фото там немає.

```json
[
	{
		"id": "label-skyr",
		"image": "photos/skyr-label.jpg",
		"text": "150 г",
		"expect": {
			"decision": "log",
			"kcal": { "exact": 96 },
			"protein": { "exact": 16.5 },
			"sources": ["LABEL"],
			"categories": ["yogurt"]
		},
		"reference": "етикетка: 64 ккал / 11 г білка на 100 г"
	},
	{
		"id": "plate-chicken",
		"image": "photos/plate-1.jpg",
		"expect": {
			"decision": "clarify",
			"kcal": { "min": 450, "max": 650 },
			"sources": ["ESTIMATE"]
		},
		"reference": "курка ~150 г, гречка ~200 г, салат; питання про олію"
	},
	{
		"id": "not-food-keyboard",
		"image": "photos/keyboard.jpg",
		"expect": { "decision": "photo_unusable" },
		"reference": "немає їжі"
	}
]
```

- `expect.sources` — кожна записана позиція має нести одне з цих джерел (етикетка → `LABEL`, страва «на око» → `ESTIMATE`); у таблиці це колонка «джерела».
- `expect.decision: "photo_unusable"` — не їжа або нечитабельна етикетка: модель має попросити перефотографувати, нічого не записавши.
- `--estimate` рахує картинку за патчами 28×28 px (1568×1176 ≈ 2 350 токенів), а не за довжиною base64.

Мінімальний набір для етапу фото: 3 етикетки (з вагою нетто; без ваги + текст «150 г»; без нічого → `clarify`), 3 страви (тарілка з олією → `clarify`; проста страва; кілька позицій), 2 «не їжа / розмито» → `photo_unusable`.

Після зміни промпту, інструментів чи моделі — прогін і рядок у `PROMPT_CHANGELOG.md` у корені.
