# Kusik — інструкції для Claude

Базовий контекст для роботи в репозиторії Kusik. Читай повністю перед будь-якою задачею. Якщо щось тут суперечить конкретному запиту в чаті — уточни, не вигадуй компроміс мовчки.

Спілкування в чаті — українською. Код, ідентифікатори, коміти — англійською.

---

## 1. Що це за проєкт

**Kusik** — AI-трекер харчування через чат. Користувач пише або фотографує, що з'їв (страву, етикетку, упаковку), AI розбирає це на записи з калоріями й макросами, перепитує, коли не впевнений, і запам'ятовує звичні продукти й порції. Чат — головний екран; решта екранів (Сьогодні, Прогрес, Рецепти, Пам'ять, Профіль) лише показує те, що AI вже записав.

- **Персона:** людина, яка хоче схуднути або тримати форму й записує їжу кілька разів на день з телефону, швидко, «на ходу». Перший користувач — автор проєкту.
- **Головний принцип UX:** внесення їжі за секунди. Кожен зайвий тап чи екран — привід кинути трекер.
- **Ринок і мова:** Польща, інтерфейс поки українською (`uk`); `pl` і `en` — пізніше, тому всі тексти одразу через i18n.
- **Mobile-first PWA** на iPhone: більшість використання — з телефону.

## 2. Стек

### Монорепо
- pnpm workspaces, Node 22 (`.nvmrc`), TypeScript strict скрізь
- `apps/web`, `apps/api`, `packages/shared` (zod-схеми, типи, промпт і AI-інструменти), `packages/ai-eval` (перевірка якості AI)

### Frontend (`apps/web`)
- React + Vite, TypeScript
- **Feature-Sliced Design** (спрощений, див. розділ 4)
- **Tailwind CSS v4** — стилі; токени через `@theme`; `cn()` (clsx + tailwind-merge) і `cva` для варіантів компонентів
- **TanStack Query** — серверний стан; **Zustand** — клієнтський стан
- **React Hook Form + Zod** — форми
- **react-i18next** — i18n (зараз `uk`)
- **React Router**, **axios**
- **Radix UI Primitives** — headless-логіка базових компонентів, стилі наші
- **Власний пак іконок** — `<Icon>` з `shared/ui/icon` (SVG → TSX генератором `apps/web/scripts/build-icons.mjs`); сторонніх бібліотек іконок немає
- **Motion** — анімації
- **date-fns** — дати
- **Recharts** — графіки (лише лінькові екрани)
- **vite-plugin-pwa** — manifest і service worker
- **Sentry** — помилки (заплановано перед бетою для інших; зараз у проєкті його немає)

### Backend (`apps/api`)
- NestJS, Prisma 7 (адаптер `PrismaPg`), PostgreSQL (Railway)
- zod для env, DTO (через `nestjs-zod`) і всього, що повертає AI
- JWT (access + refresh) в httpOnly cookie, argon2, helmet
- AI через **OpenRouter** офіційним SDK `openai` (`baseURL: https://openrouter.ai/api/v1`), модель з env `AI_MODEL`
- `image-size` — перевірка фото (без sharp: фото перекодовує клієнт), `@nestjs/throttler` — ліміти
- S3-сумісне сховище фото (Cloudflare R2, EU) — власний адаптер на `aws4fetch` у `modules/storage`, `STORAGE_PROVIDER=s3` у production

### Деплой
- api і PostgreSQL — Railway; web — Vercel; сховище фото — Cloudflare R2 (EU); помилки — Sentry (заплановано перед бетою)

Перед використанням API бібліотеки звіряйся з актуальною документацією (Context7 MCP), не з пам'яті.

## 3. Дизайн-система

**Дизайн уже готовий і лежить у `design/`.** Перед будь-якою UI-задачею прочитай `design/CLAUDE-design.md` і відкрий макет екрана з `design/docs/screens.md`. Не вигадуй вигляд, тексти, стани чи пункти меню, яких немає в макетах; бракує — запитай.

`design/` — лише для читання: не форматувати, не лінтити, не редагувати. Код звідти копіюється в `apps/web` і правиться вже там.

- Кольори, типографіка, відступи (spacing-скейл), радіуси, тіні, transition — лише через токени
- Breakpoints: mobile (основний, макети 390×844); на ширших — колонка max-width 480px по центру
- Нижня навігація: Чат · Сьогодні · Прогрес · Рецепти; Профіль і Пам'ять — через аватар
- Іконки — лише `<Icon name>` (інтерфейс) і `<FoodIcon category>` (страви). Бракує іконки — скіл `add-icon`; емодзі й сторонні бібліотеки іконок заборонені
- Вкладка «Сьогодні» — `ProgressRingIcon` (кільце заповнюється разом з днем)
- Хом'як-маскот — лише компонент `Hamster` / `HamsterHead`, лого — `LogoMark` / `Logo`

### Базові компоненти (Рівень 0 — не дублювати)
`Surface`, `Text`, `Heading`, `Button`, `IconButton`, `Input`, `Chip`, `Badge`, `Spinner` (= `Loader` з `design/src/brand`), `Skeleton`, `BaseBottomSheet`, `BaseModal`, `FormField`, `AppLayout`, `BottomNav`.

Предметні компоненти (у своїх entities/features): `MacroTile`, `Gauge`, `EntryCard`, `ClarifyCard`, `MessageBubble`, `Composer`.

Де є Radix primitive (Dialog, Popover, Tooltip, Checkbox, Tabs тощо) — беремо його заради accessibility; стилізація завжди наша. Немає primitive (bottom sheet, composer) — будуємо вручну з тими самими вимогами до a11y.

### Правила Tailwind
- Лише класи з токенів: жодних довільних значень (`bg-[#17845A]`, `p-[13px]`) і жодних inline `style`, крім динамічних значень (ширина прогрес-бару, кут шкали)
- Утиліти для розкладки (`flex`, `grid`, `gap-*`, `p-*`) можна писати прямо в слайсах
- Кольори, поверхні, радіуси, тіні, типографіка — через базові компоненти (`Surface`, `Text`, `Button`), а не набором класів у кожному місці
- Варіанти компонентів — через `cva`, злиття класів — через `cn()`
- Однаковий набір класів повторюється 2+ рази — винеси в компонент
- Порядок класів — автоматично через `prettier-plugin-tailwindcss`

## 4. Feature-Sliced Design

```
apps/web/src/
  app/        # провайдери, роутер, глобальні стилі
  pages/      # chat, today, progress, recipes, profile, memory, auth, onboarding
  widgets/    # chat-feed, day-summary, bottom-nav
  features/   # send-message, edit-entry, answer-clarify, save-recipe, log-weight
  entities/   # entry, message, recipe, my-food, stats, user
  shared/     # ui (Рівень 0 + theme), api, lib, config, i18n
```

- `entities/` — читання й відображення даних, `features/` — дії й мутації
- Без cross-feature imports: одна feature не імпортує з іншої
- Кожна нова папка-слайс одразу отримує `index.ts` (barrel). Перевіряй явно перед тим, як вважати слайс готовим
- Похідний стан — «adjust state during render», не `useEffect`
- Prop drilling через 3+ рівні або приховані залежності від глобального стану — сигнал зупинитись і перевірити межі шару

### Naming
- Папка компонента — kebab-case (`entry-card/`), файл — PascalCase (`EntryCard.tsx`)
- Допоміжні — kebab-case із суфіксом (`entry-card.types.ts`, `entry-card.variants.ts`)
- Хуки — camelCase (`useDayStats`), i18n-ключі — dot notation (`chat.composer.placeholder`)

## 5. Backend

```
apps/api/src/
  modules/<feature>/   # auth, users, chat, ai, entries, stats, memory, weight
    <feature>.module.ts
    <feature>.controller.ts
    <feature>.service.ts
    <feature>.repository.ts
    dto/
  common/              # guards, filters, interceptors, decorators, exceptions (AppException, ErrorCodes)
  config/              # env-схема (zod)
  prisma/              # PrismaService
```

### Архітектура модуля
- Кожен модуль: `module / controller / service / repository / dto`
- **Repository** — лише Prisma-запити, без бізнес-логіки; приймає опціональний `tx?: Prisma.TransactionClient`
- **Service** — бізнес-логіка й транзакції
- **Controller** — тонкий: валідація, виклик сервісу, формат відповіді
- Cross-module доступ — лише через сервіси іншого модуля, ніколи напряму в чужий repository
- Guards комбінуються в один `@UseGuards(...)`; користувач — `request.user.sub` (JWT payload), не `request.user.id`
- Роут `/me` реєструється **перед** `/:id`
- API-префікс `/api/v1/...`; роути — kebab-case у множині

### Дані
- Prisma 7 з адаптером `PrismaPg`, PostgreSQL на Railway
- Схема спроєктована одразу на весь домен, реалізація — по roadmap. Моделі: User, AuthCredentials, Session, VerificationToken, UserProfile, UserGoal, Measurement, Achievement, Message, MessageAttachment, AiRun, AiToolCall, Clarification, ClarificationEntry, Meal, FoodEntry, MyFood, Recipe, RecipeIngredient, Correction, UserFact, DailyUsage, ExerciseEntry, StoredFile. Опис і діаграма — `docs/database.md`
- Enum'и схеми дзеркаляться zod-enum'ами в `packages/shared/src/schemas/enums.ts` — змінюєш одне, змінюй і друге
- Перед додаванням поля чи моделі — перевір актуальну `schema.prisma`, не опис у документах
- Soft delete (`deletedAt`) для записів користувача (Meal, FoodEntry, MyFood, Recipe, UserFact, ExerciseEntry, Measurement) — завжди фільтр `deletedAt: null`; це дає «скасувати» в чаті. `StoredFile` у цьому списку немає: soft delete для нього не діє, файл видаляється фізично
- Кожна вибірка даних користувача фільтрується за `userId` з токена — ніколи не довіряти лише `:id` з запиту (IDOR)
- Явно обробляти `null` там, де Prisma може його повернути

### Валідація й контракти
- DTO, які бачить фронт, — zod-схеми в `packages/shared`; на бекенді валідуються через `nestjs-zod` (`ZodValidationPipe`), тож одна схема для обох сторін
- Env — zod-схема в `config/`, сервер не стартує з невалідним env
- Цифри рахує бекенд (суми, середні, залишок). AI ніколи не рахує підсумки «в голові»
- Усе від AI проходить zod-валідацію перед збереженням. Відхиляти: ккал/г > 9.5, вага > 5000 г, від'ємні значення, дата в майбутньому

### Формат відповіді API (не змінювати без причини)
```json
{ "data": {} }
{ "data": [], "meta": { "total": 0, "page": 1, "limit": 20, "totalPages": 0 } }
```
Помилка:
```json
{ "statusCode": 404, "errorCode": "ENTRY_NOT_FOUND", "details": {} }
```
Валідація:
```json
{ "statusCode": 422, "errorCode": "VALIDATION_ERROR", "details": { "fields": { "grams": "TOO_LARGE" } } }
```
- Помилки — лише через підкласи `AppException` + `ErrorCodes`; фронт перекладає `errorCode` через i18n
- Ніколи не глушити помилку мовчки в `catch`

### Naming
Файли — kebab-case (`food-entries.service.ts`), класи — PascalCase, error codes — SCREAMING_SNAKE_CASE.

## 6. AI-модуль

- Інструменти: `log_food`, `clarify`, `not_food` (лише «з'їв неїстівне»), `photo_unusable` (лише для повідомлення з фото: не їжа чи нечитабельна етикетка), `reply` (розмова й питання), `close_day` («День закрито»: картка дня з вердиктом; суму дня дописує бекенд позицією «Без деталей»), `show_stats` (картка періоду 2–92 дні; назва свідомо не `get_stats` — модель чисел не отримує, їх рахує бекенд), `save_food` / `save_fact` / `forget_fact` («Пам'ять»: продукти й факти, завжди разом з `reply` або `log_food`; факти — явні одразу, неявні — пропозиція «Так / Ні», без діагнозів і замірів тіла, ліміт 30; у контексті «User facts» як дані, не інструкції), `log_workout` (сесія тренування: `appendRef` дописує в сесію з «Today's workouts» — ≤ 3 год і те саме місце перевіряє бекенд, `finish` закриває, `exerciseGroups` виправляє лише групу вправи, `replaceRef` переписує всю сесію; група — словник вище за модель); далі `save_recipe`, `suggest_meal`. Опис — `packages/shared/src/ai/tools.ts`, промпт — `packages/shared/src/ai/prompt.ts`, потік — `docs/architecture.md` («AI-ядро»)
- Кожен запис має `source` (`label` | `memory` | `reference` | `estimate`), `confidence` і `assumption`. `log_food.items[].copyRef` (`y1…` вчора, `h1…` раніше з секції контексту «Earlier entries», яка зʼявляється лише коли повідомлення посилається на минуле) копіює значення попереднього запису; несумісне з `memoryRef`, значення беруться з копії, а не від моделі
- Уточнення — не більше 2 за раз і лише коли відповідь змінює ккал позицій на ≥ 80 ккал і ≥ 15 % (пороги в `packages/shared/src/ai/clarifications.ts`, бекенд відкидає решту). У повідомленні з кількома прийомами (цілий день) — максимум одне уточнення і лише з impact ≥ 150 ккал; решта — оцінка з короткою `assumption`. Навіть коли питає, AI записує найкращу оцінку
- Тип прийому — на позицію (`log_food.items[].mealType`), інакше загальний `mealType`, інакше за локальною годиною; бекенд групує позиції в Meal за типом, відповідь API — `meals[]`
- Фото: двокроковий потік — `POST /photos` (повне + мініатюра, base64 JPEG), потім `POST /messages` з `photoIds` (до `PHOTOS_PER_MESSAGE_MAX` ≤ 6; AI поки читає одне). Клієнт перекодовує будь-який формат (HEIC теж) через canvas у JPEG: повне ≤ 1568 px / ~1 МБ, мініатюра 768 px ≤ 150 КБ — без EXIF; `photoId` лежить в outbox, повтор не вантажить вдруге. Бекенд приймає лише JPEG: magic bytes, `image-size`, зрізає метадані (APPn/COM) і хвіст після EOI. Фото зберігається в приватному S3-сумісному сховищі (Cloudflare R2 EU) під `<prefix>/users/<userId>/photos/<id>[-thumb]`; в БД — `StoredFile` і `MessageAttachment` (без байтів). Віддає лише API (`GET /photos/:id?variant`), чуже = 404, SW не кешує. Фото ніколи не потрапляє в логи. Ліміти: `PHOTO_DAILY_UPLOAD_LIMIT` (завантаження), `AI_DAILY_PHOTO_LIMIT` (відправка моделі). Сироти (24 год) і файли видаленого акаунта чистять крони. Деталі — `docs/architecture.md`
- Контекст моделі: промпт + релевантна пам'ять + підсумок дня + кілька останніх повідомлень. Ніколи вся історія
- Логувати токени й вартість кожного запиту; денний ліміт повідомлень на користувача
- Після зміни промпту, контексту моделі чи моделі — eval за розділом 8.1 (п. 6): спершу нові кейси через `--only`, повний прогін — раз на версію промпту; рядок у `PROMPT_CHANGELOG.md`
- Тон: теплий, короткий, без сорому й моралізаторства. Без медичних порад і екстремальних дефіцитів. Теми розладів харчування — м'яко, без цифр, з порадою звернутися до фахівця

## 7. Правила коду

- Лише стрілкові функції (`const fn = () => {}`), без `function`-декларацій і `forwardRef`
- Ніколи `any` — тільки `unknown` + narrowing; якщо зовсім не уникнути — коментар чому
- Явна типізація, без важкого inference з generic-ланцюжків
- Guard clauses / early return замість вкладених if-else
- Одна функція/компонент — одна відповідальність; options-об'єкт замість кількох boolean-параметрів
- Функції — дієслово (`getDayStats`), булеві — `is/has/can/should`, без `tmp`/`data2`/`val`
- **Жодного хардкоду рядків UI** — усе через `t('key')`, навіть «тимчасове»
- Логіка — у hooks/lib, компоненти презентаційні
- Магічні числа й рядки — в іменовані константи
- Файл > ~150–200 рядків — сигнал розбити
- Виносимо в спільне лише при 2+ повтореннях
- Без невикористаних імпортів і змінних, без залишків debug-коду; бачиш таке — прибирай одразу

### Гігієна файлів
- Якщо для категорії вже є спільне місце (токени, анімації, хуки, константи) — розширюй його, не створюй паралельне визначення
- Один файл — один тип вмісту: `.types.ts`, `.variants.ts` (cva), константи, утиліти — окремо; компонент — JSX + виклик хуків

### Коментарі
- Мінімум: пояснюють «чому», не «що»
- Без закоментованого мертвого коду; перед комітом прибрати зайве

### Форми
- React Hook Form + Zod, схема через `createXxxSchema(t)` для перекладених помилок
- `FormField` + `Controller`, не прямий `register` в обхід спільного компонента
- Валідація на ходу (onChange); помилка одразу під полем, конкретна
- Submit не блокується до валідності — краще показати всі помилки після натискання

### Анімації
- Лише через Motion, на пресетах з `shared/lib/motion` (`TRANSITION`, варіанти); у корені `<MotionConfig reducedMotion="user">`
- Виняток: нескінченні петлі з `design/src` (лоадер, «друкує…», кліпання хом'яка) лишаються на CSS

### Самоперевірка після задачі (обов'язково)

Задача не вважається виконаною, поки ти сам не перевірив результат. Після кожної задачі запускай скіл **`/verify`** (`.claude/skills/verify/SKILL.md`) і проходь його чекліст для бекенду, фронтенду й AI — тих частин, яких торкалася задача.

- «Перевірено» означає: команду реально запущено й результат побачено. Не запускав — пиши «не перевірено» і чому
- Знайшов проблему під час перевірки — виправ і перевір заново, не звітуй з відомою помилкою
- Для задач більше ~1 години або тих, що зачіпають auth, дані користувача чи AI-промпт — після власної перевірки запусти субагента **`reviewer`** (`.claude/agents/reviewer.md`): він дивиться на diff свіжим поглядом
- Завершуй задачу звітом у форматі зі скіла `/verify`

### Вибір моделі й субагентів (економія лімітів)

Основна сесія — Sonnet (`/model sonnet`). Роботу делегуй субагентам із `.claude/agents/` за складністю, починаючи з найдешевшого, що підходить.

| Агент | Модель | Коли |
|---|---|---|
| `fast` | Haiku | пошук по монорепо, читання й підсумок коду/логів/diff, прогін `lint` / `typecheck` / тестів зачеплених пакетів зі звітом (розділ 8.1), рядки в `uk.json`, дрібна правка в 1 файлі за готовою інструкцією, текст коміту |
| `builder` | Sonnet | скіли `screen-from-mockup`, `new-ui-component`, `new-fsd-slice`, `add-empty-state`, `add-icon`, `add-hamster-mood`, `add-sound`, `add-design-token`, `add-food-category`, `new-api-endpoint`; баги з відомою причиною; тести; реалізація плану від `architect` |
| `architect` | Opus | п. 4 цього розділу (архітектура, trade-offs), скіли `add-prisma-model` і `add-ai-tool` — етап рішення, auth / ізоляція даних, AI-ядро, рефакторинг на 6+ файлів, баг без очевидної причини. Лише план, без коду |
| `reviewer` | Sonnet | як описано вище, після задач понад ~1 годину або з auth / даними користувача / AI-промптом |
| `test-writer` | Sonnet | з `/verify`: нова логіка без тестів |
| `ui-checker` | Sonnet | з `/verify`: змінився вигляд екрана — скриншот 390 px проти макета, стани, a11y |
| `copy-i18n` | Haiku | з `/verify`: змінились тексти чи `uk.json` — хардкод, ключі, тон |
| `ai-eval-analyst` | Sonnet | зі скіла `add-ai-tool` і `/verify` після eval; порівняння моделей OpenRouter за ціною й точністю |
| `security-audit` | Sonnet | перед кожним `git push` (режим push, див. розділ 9); повний — перед закриттям етапу roadmap |

Правила:
1. **Сумніваєшся між рівнями — бери нижчий.** Ескалація — лише коли агент повернув «складніше, ніж …» або дві спроби не вдались.
2. **Opus планує, Sonnet виконує.** План `architect` реалізує `builder`; Opus не пише код і не читає зайвого.
3. **Контекст збирає `fast`.** Не запускай дорогу модель на пошук файлів і прогін тестів.
4. **Групуй дрібниці** в одне завдання для `fast`, а не кілька викликів.
5. **Передавай мінімум.** Агенту — шляхи, факти й чітке завдання, не весь діалог.
6. **Без агента, якщо простіше.** Коротке питання чи правка в один рядок — одразу в основній сесії: запуск агента теж коштує.
7. **Промпт AI (`prompt.ts`) змінюється лише дослівно затвердженим Богданом текстом і за його явним дозволом у цій сесії.** Зміна завжди окремо показується в диффі й проходить текстовий eval перед деплоєм. Агенти можуть лише запропонувати текст.
8. **`pnpm --filter ai-eval eval` коштує грошей OpenRouter** — лише після зміни промпту, моделі чи AI-інструментів, і лише в основній сесії. Нові кейси — через `--only`, повний прогін — раз на версію (розділ 8.1, п. 6).
9. **`pnpm test` / e2e — лише один прогін одночасно:** усі e2e ділять базу `kus_test` і чистять її (TRUNCATE) перед кожним тестом. Агенти не запускають тести паралельно; якщо прогін уже йде — чекати його завершення.

## 8.1. Економія тестів

Тести коштують часу й ліміту: повний прогін (`apps/api` ~10 хв) — рідко, точкові — часто.

1. **Тест-агенти — лише свої файли.** `test-writer` і `builder` запускають лише нові/змінені тест-файли: `pnpm --filter <pkg> exec vitest run <файли>`, не весь пакет. Червоне на старому коді перевіряється лише цими файлами.
2. **На коміт — одна повна перевірка від `fast`, лише в зачеплених пакетах:** `typecheck` + `lint` + тести. Для `apps/web` і `packages/shared` — `pnpm --filter <pkg> exec vitest related --run <змінені файли>`. **Для `apps/api` `vitest related` не використовуємо** (він тягне забагато e2e, прогін виходить за ~2 хв): `fast` запускає явний список — unit-спеки змінених модулів і e2e-спеки тих endpoint-ів чи потоків, які змінює коміт (`pnpm --filter api exec vitest run <файли>`); список файлів — у звіті. Решту e2e покриває повний `pnpm test` наприкінці етапу (п. 4). Незачеплені пакети не ганяємо. Якщо зачеплено `packages/shared` — спершу `pnpm --filter @kus/shared build`, як у `typecheck` кореня.
3. **`git stash push --keep-index` — лише за потреби.** Перевірка індексу потрібна, лише якщо після `git add` у дереві лишились незастейджені зміни (`git diff --quiet` дає ненульовий код). Інакше пропускаємо: на коміті вже працюють husky + lint-staged.
4. **Повний `pnpm test` (усі пакети, зокрема api) — один раз наприкінці етапу**, перед `security-audit` full. Не після кожної задачі й не на кожен коміт.
5. **`reviewer` тестів не запускає** — рев'ю лише за diff.
6. **Eval — лише коли змінюється `prompt.ts` або контекст моделі** (зміна самої моделі — за `add-ai-tool`: спершу `--estimate`, потім 2–3 кандидати). Спершу лише нові кейси (`--only <id,...>` з `--max-cost`); повний прогін — один раз на версію промпту.
7. **Звіти короткі:** таблиця результатів, що змінено, що не перевірено, текст коміту. Без переказу плану.

## 9. Git

- **Ніколи не роби `git commit` чи `git push` без явної команди в чаті** («закоміть», «запуш») — навіть якщо задача завершена й усе зелене
- **Перед кожним `git push`** — субагент `security-audit` у режимі push (лише `origin/main..HEAD`): пуш у `main` = деплой. Вердикт «⛔ не пушити» — не пушити, показати знахідки й чекати рішення
- Соло-розробка: працюємо напряму в `main`, `main` — завжди робочий стан
- Conventional commits англійською (`feat:`, `fix:`, `chore:`, `refactor:`, `docs:`), розбиті по логічних групах
- **Кожен коміт компілюється сам по собі:** lint + typecheck проходять на вмісті саме цього коміту, а не всього робочого дерева. Файли, що залежать один від одного (імпорт, тип, i18n-ключ, токен-клас), — в одному коміті або в порядку залежностей: спершу те, від чого залежать
  - Husky перевіряє робоче дерево, тож незакомічені файли можуть маскувати поламаний коміт. Перевірка індексу — лише якщо після `git add` у дереві лишились незастейджені зміни (розділ 8.1, п. 3): `git stash push --keep-index --include-untracked` → `pnpm lint && pnpm typecheck` → `git stash pop`. Інакше пропускаємо
- **Не запускай `build` у `apps/api/dist`, поки працює dev-сервер** (`pnpm dev` / `nest start --watch` бере код звідти, і `nest build` його валить). Для перевірки — лише `pnpm typecheck`; якщо потрібен зібраний API — `pnpm --filter api exec tsc -p tsconfig.build.json --outDir <тимчасова тека поза репо>`
- Перед `git add` — `git status`, свідомо обирати файли (не `add .` наосліп)
- Після заміни `design/` новим архівом — `design/` комітиться **окремим** комітом `chore(design): <що змінилось за верхнім записом design/CHANGELOG.md>`, ніколи не разом з кодом (і, як завжди, лише за командою)
- Husky + lint-staged блокують коміт з помилками lint/typecheck
- **Реліз** (`chore: release X.Y.Z`, версія в `apps/web/package.json`, анотований тег `vX.Y.Z` на `main`) не завершений без трьох речей: секція `[X.Y.Z]` у `CHANGELOG.md` (Keep a Changelog, англійською, з посиланнями на коміти), запис у `apps/web/src/shared/config/release-notes.ts` (2–4 рядки українською для користувача, без технічних слів, нейтрально щодо статі) і GitHub Release на тезі з текстом секції з CHANGELOG (`gh release create vX.Y.Z --notes-file …`; без `gh` — дати користувачу готовий текст)
- Репозиторій **публічний**: жодних секретів і реальних особистих даних (раціон, вага, фото) у комітах

## 10. Безпека

Правила тут пріоритетніші за швидкість. Для auth і будь-яких мутуючих ендпоінтів перевіряй цей розділ явно.

### Auth
- Паролі — лише хеш (argon2) в `AuthCredentials.passwordHash`
- JWT access — короткоживучий; refresh — довгоживучий, зберігається як хеш, ротація через `tokenFamily`; повторне використання вже вжитого refresh — інвалідовувати всю `tokenFamily`
- `failedLoginAttempts` / `lockedUntil` — реально блокують brute-force
- Токени — `httpOnly`, `secure`, `sameSite` cookie від бекенду; не в `localStorage`/`sessionStorage`
- v0.1: email + пароль; підтвердження email, скидання пароля (Resend) і Google OAuth — перед бетою для інших

### Rate limiting
- `@nestjs/throttler` на всіх auth-ендпоінтах, жорсткіше на `/login`; ліміт по IP і по акаунту
- Окремий денний ліміт повідомлень у чат і фото на користувача (захист бюджету AI)

### Транспорт і заголовки
- `helmet` глобально; CORS — явний allowlist (домен Vercel + localhost), ніколи `*` у проді; лише HTTPS

### Ізоляція даних
- Кожен запит до даних користувача фільтрується за `userId` з токена; якщо ендпоінт приймає `:id` — сервіс явно перевіряє, що сутність належить користувачу (IDOR)

### Вхідні дані
- Усі DTO валідуються до сервісу; клієнтська валідація — лише UX
- Фото: на бекенді перевіряються тип (лише JPEG, magic bytes), розміри (`image-size`) і розмір (повне ≤ 1,4 МБ, мініатюра ≤ 150 КБ); метадані й хвіст після EOI зрізаються; доступ до файлу — лише за `userId` з токена
- Лише Prisma query builder; raw SQL — тільки параметризований
- Текст від користувача й AI на фронті виводиться лише як текст, без `dangerouslySetInnerHTML`

### Секрети й залежності
- `.env` не комітиться, секрети — лише через змінні Railway/Vercel; `withCredentials` лише для власного API
- **Ніколи не створювати й не перезаписувати `.env`-файли командами** (`cp`, `>`, `tee`, Write тощо) — навіть з `.env.example`. Якщо `.env` потрібен чи в ньому бракує змінної — сказати користувачу, що саме туди вписати
- `pnpm audit` — регулярно

### Приватність
- Дані про харчування, вагу й фото — чутливі (RODO): у запит до AI — лише потрібний мінімум; фото зберігаються в приватному сховищі, віддаються лише власнику, не логуються; у v1 — експорт (разом з фото), видалення всіх даних і строк зберігання фото (поки його немає)

## 10.1. Логування

- Бекенд — NestJS `Logger` з контекстом (`new Logger(EntriesService.name)`), не `console.log`; фронт — Sentry (заплановано перед бетою; поки лише логи бекенду)
- Рівні: `error` — збої, `warn` — підозріле, `log` — важливі події (реєстрація, невдалий логін, помилка AI), `debug` — лише в dev
- Для AI логуємо метадані: модель, токени, вартість, тривалість, кількість викликів інструментів — без вмісту повідомлень
- **Ніколи не логуємо й не відправляємо в Sentry (коли він з'явиться):** паролі, хеші, токени, API-ключі, `DATABASE_URL`, тіло auth-запитів, текст повідомлень і фото користувача, вагу, записи їжі. За потреби — лише ідентифікатори (`userId`, `entryId`)
- Сумнів, чи безпечно логувати — не логуємо

## 11. Продуктивність

- Code-splitting по роутах (`React.lazy` + `Suspense`); Recharts і важкі екрани — лише лінькові
- TanStack Query: retry з backoff для мережевих помилок (не для 4xx), свідомий `staleTime`, явний стан «не вдалося — повторити»
- Фото: стиснення й ресайз на клієнті перед відправкою, `loading="lazy"` для зображень
- Відповіді AI — стрімінг (SSE), щоб не чекати повну відповідь

## 12. Loading / Empty / Error

- **Skeleton** — для завантаження з відомою структурою (стрічка чату, картки дня); повторює форму контенту
- **Spinner** (`Loader`) — лише для коротких дій і першого старту; показувати після 300 мс (`useDelayedFlag`)
- **AI думає** — індикатор «друкує…» у стрічці чату
- **Empty** — візуально й текстово відрізняється від помилки, з закликом до дії («Напиши, що з'їв»)
- **Error** — inline на місці блоку для помилок завантаження; toast — для помилок дій

---

## 13. Accessibility

- Контраст тексту й інтерактивних кольорів — мінімум WCAG AA, перевіряти при додаванні токена
- Звук (`playSound`) — лише разом з візуальним відгуком, ніколи замість нього
- Тап-таргети ≥ 44×44 px
- `prefers-reduced-motion` враховується в усіх анімаціях
- Колір ніколи не єдиний носій сенсу (макроси — підпис + колір)
- Ручні компоненти — ті самі вимоги до aria, клавіатури й фокусу
